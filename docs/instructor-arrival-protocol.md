# Protocol for a supplementary arrival experiment

This protocol specifies a bounded, exploratory experiment on the relation between externally scheduled layer work, service time, and queueing. It addresses an omission in the original proposal: changing token-batch size or expert-hotspot identity does not by itself vary arrival rate. The experiment will use previously observed development inputs and one new allocation. It is a supplementary validation of a service model, not a new confirmatory test of the completed migration gate or resident dispatcher. The historical protocols, source fingerprints, final records, thresholds, and conclusions will remain unchanged.

A service job is one invocation of the existing distributed MoE layer with a fixed number of captured token records. Let $B$ denote the number of tokens in a job, and let $N$ denote the number of jobs in a trial. The experiment fixes $N=256$ and considers $B=128$ and $B=1024$. Each job retains its captured hidden states, logical top-8 expert IDs, and combining weights. The arrival schedule is synthetic; the token payload is taken from genuine teacher-forced causal-prefill captures. Separate jobs will not be combined into an inter-request batch, and no job will be split, dropped, or replaced to satisfy its schedule. A job is therefore a layer-service unit, not a complete language-model request.

An input state is one combination of a development source-document pair, one of its two captured domains, and a token-batch size. The two existing development pairs, their prose and Python-code domains, and the two batch sizes give eight states. The state definitions and captured-index sequences will be pinned before measurement. These inputs are already development data; reusing them does not create eight new independent workloads. The same ordered sequence of 256 payloads will be used for every arrival pattern, offered load, arm, and repetition of a state. Repeated captured inputs and repeated timing trials do not increase the number of source-document pairs.

The two arms are the unchanged native resident dispatcher and the previously frozen online current-batch dispatcher. Both will use the same fixed resident map, pretrained expert tensors, native expert kernels, output collective, and always-skip migration policy. Each job will execute the native observation and step path, including nonterminal planning. No expert migration will be admitted. The final proposal will be suppressed under the existing terminal-input contract. Input materialization, compilation, numerical preflight, and common state conditioning will remain outside the scheduled trial and will be recorded separately. The previously declared event initialization and full-policy conditioning will apply to both arms; observation state will be reset before the first measured job.

The apparatus remains one BF16 Qwen3-30B-A3B layer 0, with hidden width 2048, intermediate width 768, 128 logical experts, top-8 routing, and 32 redundant copies. The 160 physical slots are divided equally between two H100 GPUs. Both ranks receive the same logical input batch and combine local expert outputs with the existing all-reduce. The placement and software pins will be inherited from the resident-dispatch study. This experiment will not change model architecture, GPU architecture, expert budget, or transport implementation.

All scheduled and measured wall-clock timestamps will use the rank-0 monotonic clock. Let $o$ denote the absolute trial origin. For job index $i$, beginning at zero, let $a_i$ denote its predetermined release timestamp, $e_i$ the time at which rank 0 observes and admits that job at the head of the queue, $s_i$ the time immediately before rank 0 issues its service command, and $f_i$ the time after rank 0 has received completion acknowledgements establishing that both ranks have completed the job's GPU work. The timestamp $e_i$ is an admission observation. It is not an independently measured external enqueue event and will not replace $a_i$ in latency calculations.

The service discipline will be first-come, first-served, with increasing job index breaking simultaneous-arrival ties. At most one job will be in service. Rank 0 will wait against the absolute release calendar when the next job is not yet due, issue a command through a CPU Gloo control path, perform its own layer work, and receive the GPU-complete acknowledgements. The next job will not start before the previous acknowledgement completes. CPU command distribution, coordination, GPU synchronization, and acknowledgement costs are consequently part of the observed service interval. Sleep and wake-up delays affect the actual admission and start timestamps and remain visible. No latency measurement will subtract timestamps from unsynchronized rank clocks.

The calendar will remain immutable while the server is busy. If several release times pass during a service interval, those jobs will retain their original release times and wait in order. This requirement prevents completion-dependent rescheduling from concealing queueing delay. Valid timestamps satisfy $a_i\leq e_i\leq s_i\leq f_i$, and for every job after the first, $e_i\geq f_{i-1}$. The implementation will retain both the calendar and observations so that an independent audit can reject early starts, overlapping jobs, changed release times, and missing completions.

The per-job queueing-plus-admission delay is $Q_i=s_i-a_i$, the charged service interval is $S_i=f_i-s_i$, and the response interval is $L_i=f_i-a_i=Q_i+S_i$. The additional decomposition into $e_i-a_i$ and $s_i-e_i$ will distinguish delayed admission observation from the interval between observation and command issue. These definitions deliberately include the costs of this synchronized service wrapper. They do not estimate the response time of vLLM's full serving scheduler or isolate expert-kernel execution from CPU coordination.

Capacity will be calibrated separately for each state using the native arm alone. Each of the eight calibrations will run 256 back-to-back jobs through the new synchronized first-come, first-served command-and-acknowledgement path after common conditioning. Let $s^{\mathrm{cal}}_0$ be its first command-start timestamp and $f^{\mathrm{cal}}_{N-1}$ its last completion timestamp. The reference capacity is

$$
C_{\mathrm{native}}=
\frac{N}{f^{\mathrm{cal}}_{N-1}-s^{\mathrm{cal}}_0}.
$$

Capacity is measured in jobs per second. Its reciprocal is the mean saturated cycle time, including between-job server bookkeeping; it need not equal the average of the individual $S_i$ intervals. The calibration will not reuse throughput from the earlier back-to-back resident-layer timing boundary. The native calibration result for a state will be recorded once and used for both arms and every schedule in that state. The online arm will not determine an offered rate, and a slow calibration will not be replaced selectively.

Let $\rho$ denote offered load relative to this native reference capacity, and let $\lambda=\rho C_{\mathrm{native}}$ denote the scheduled rate in jobs per second. The two fixed values are $\rho=0.50$ and $\rho=0.85$. These labels are reference load fractions, not assertions that either arm has exactly 50% or 85% GPU utilization. The online arm has the same external calendar as its native comparator; it will not receive a separately rescaled load. Let $H=N/\lambda$ denote the nominal release horizon in seconds. Both arrival patterns will have 256 jobs and the same $H$ at a given state and load.

The constant pattern will release job $i$ at offset $i/\lambda$. The burst pattern will release groups of eight jobs simultaneously, with group starts separated by $8/\lambda$. Thus its job-$i$ offset is $8\lfloor i/8\rfloor/\lambda$. There are 32 bursts. Both patterns begin at offset zero, and all releases precede the common nominal horizon. Their last release times differ; equal horizon here means the explicitly recorded interval from zero to $H$, not an asserted equality of first-to-last-arrival spans.

The implementation will construct the calendar in integer nanoseconds. Offered-load fractions will be represented exactly from their decimal strings, and each ideal offset and horizon will be rounded to the nearest nanosecond with ties to even. The resulting integer offsets and their checksums will be retained. Each trial's absolute calendar will add its rank-0 origin to the same paired offsets. Runtime delays will not change those offsets.

The evaluation contains eight states, four schedules per state (two arrival patterns crossed with two loads), two dispatch arms, and two technical repetitions: 128 evaluation trials. Each trial contains 256 jobs, giving 32,768 evaluation jobs in addition to the 2,048 calibration jobs. One allocation will contain the complete bounded experiment. A seeded, frozen order will identify all state/schedule pairs. Within each pair the two arms will run in one order for the first repetition and the reverse order for the second. There is no additional rate grid, burst-size grid, controller search, or outcome-dependent repetition count.

Every complete trial will drain all 256 jobs. The nominal horizon is not a censoring deadline. If work remains at that horizon, its completion will contribute to the reported drain interval. If all jobs finish earlier, the observation contract will retain the remaining scheduled idle portion through the common horizon. The ideal observation extent is $\max(H,f_{N-1}-o)$, and the post-horizon drain is $\max(0,f_{N-1}-o-H)$. Actual final observation timestamps and any wake-up overshoot will be recorded separately. The report will give the number of released jobs still unfinished at the horizon, separating a job in service from jobs awaiting service when applicable.

All non-service intervals will remain visible in the timestamp record. In particular, the gaps between a preceding completion and the next command start include scheduled idle time, wake-up delay, and controller bookkeeping. They will not be relabelled as pure GPU idle time without separate evidence. Completed throughput over the full observation interval will be reported alongside service and response statistics. At low offered load, identical scheduled horizons can make elapsed trial time nearly identical even when individual service times differ; that is a consequence of the finite arrival experiment, not evidence that a faster service path has no effect.

Native statistics retain their original job-count geometry. Let $W$ denote the number of jobs in an observation window and $R$ the interval between planning opportunities; their fixed values remain $W=16$ and $R=64$. They are not millisecond intervals. For each observed window, the raw record will retain its exact job-index range, scheduled release times, command-start times, completion times, physical assignment counts, and reconstructed logical counts. Its executed span in seconds will be the last completion minus the first command start within that window; its scheduled-arrival span will be reported separately. This distinguishes the same 16-job statistic observed over different wall-clock durations under constant and burst arrivals.

The prespecified queueing hypothesis is that simultaneous releases can increase waiting and upper response quantiles relative to the constant pattern at the same offered load, even when per-job numerical work is unchanged. A second hypothesis is that a service-time difference can have a larger effect on queueing near the higher native reference load than under a lightly loaded calendar. A third, architecture-conditioned hypothesis is that the selector's fixed launch and coordination costs can outweigh reductions in activated expert work for the smaller token batch, whereas the larger batch may amortize those costs. These are directional mechanisms to examine in this supplementary experiment, not universal queueing theorems or new claims of cross-architecture portability. The direction of each effect can be contradicted by the measured paired observations.

The descriptive report will retain every state, arrival pattern, load, arm, and repetition. It will report means, medians, 95th and 99th percentiles, and maxima of response, queueing, service, admission-delay, and dispatch-delay intervals, together with completion counts, backlog, and drain. Percentiles will use linear interpolation of the finite sample. Quantiles describe the finite set of observed jobs, which reuse payloads and are temporally dependent. The two technical repeats will be shown as repeats, not new source blocks. The two development document pairs and one allocation do not support a production-workload or hardware-population confidence interval. There will be no confirmatory latency confidence intervals, performance acceptance decision, retrofit of the historical 5% criterion, or change to a previously frozen parameter based on this result.

Numerical correctness, logical-route preservation, fixed maps and expert weights, rank agreement, native observation counts, and zero migration will remain required invariants. Missing jobs, duplicate jobs, early starts, incomplete drains, invalid timestamps, and correctness failures will be reported explicitly. A wall-time limit or process failure will produce a retained incomplete attempt; the surviving responses will not be reported as a complete-run latency distribution. No slow job or timeout will be filtered from an otherwise claimed complete trial. Any necessary implementation correction will be documented and frozen before a replacement attempt, without overwriting the original evidence.

The vLLM serving benchmark provides a useful convention for distinguishing a requested arrival rate from request size and completion latency. At the exact source pin used in this project, its generator defines request rate in requests per second and uses Poisson arrivals at a burstiness parameter of one, with gamma-distributed intervals otherwise; self-timed inputs bypass those generated intervals. This experiment instead specifies deterministic constant arrivals and fixed bursts of eight. It does not equate a burst of eight with a vLLM burstiness value and does not claim to run the serving benchmark or its scheduler. [Pinned vLLM serving benchmark](https://raw.githubusercontent.com/vllm-project/vllm/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/benchmarks/serve.py).

The capacity calibration and all evaluation trials will run without an intrusive profiler or concurrent diagnostic probe. NVIDIA documents that detailed Nsight Systems collection can alter application timing and recommends validating improvements with unprofiled measurements. Any later profile will therefore be a separate diagnostic with its own provenance, not a source of primary response-time samples or a subtraction from measured overhead. Existing profile results do not establish a hardware roofline for this new synchronized wrapper. [NVIDIA Nsight Systems User Guide, profiling overhead](https://docs.nvidia.com/nsight-systems/UserGuide/index.html).

Before GPU execution, the experiment manifest will bind this protocol, implementation and analysis hashes, exact development input identities, native and online source pins, complete trial order, calibration rule, release-calendar rule, and timing definitions. Calibration will populate only the prespecified native capacity values and their derived calendars. It will not select a different policy, margin, workload, or architecture. The resulting observations will remain a separate exploratory supplement to the completed studies.
