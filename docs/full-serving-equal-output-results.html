Equal-output-length full-model results

No observed response-latency speedup over native vLLM with EPLB OFF. With each prompt forced to the same output-token count across methods, our mean response is 2.52% slower on LongBench and 0.47% slower on NuminaMath. Against EPLB ON, NuminaMath mean response is 10.82% lower and completed elapsed time is 3.21% lower; LongBench mean response is 1.64% higher. This is a measured matched-length end-to-end gain against ON on this NuminaMath episode, not a repeatable or general advantage over OFF.

All six sessions completed on eight reserved H100s (kh074/kh077), using the full pinned Qwen3-30B-A3B checkpoint. All 96 measured requests and 96 warmup executions completed with their exact per-request output targets and length termination. No requests were dropped, no measured preemptions occurred, and no algorithm or workload setting changed during the run. Independent raw-timestamp reconstruction passed, 226 public files match stable remote bytes, and 49 executing source files match commit 6a6187a8e8e6aa65f9aff7c008de599c93c37f55. Remote analysis and fresh CPU reconstruction agree; this verifies the calculations, not experimental replication.

There are two datasets, one group of sixteen requests per dataset and three methods. Each method uses the same prompts and absolute arrivals within a dataset. Each request's target is its previous natural-stopping OFF completion count, frozen before this comparison. The client uses min_tokens=max_tokens=N and suppresses early stopping. Targets sum to 162 LongBench and 17,519 NuminaMath output tokens per method. These are new executions of previously used content and calendars; they are not a new generalization sample. Both warmup passes use separate frozen pilot targets. See the protocol and output-divergence diagnosis.

Response is scheduled arrival to completed HTTP response, including waiting and generation. TTFT is scheduled arrival to first nonempty streamed content. Elapsed is the entire offered arrival horizon plus drain; drain is time from that horizon's end to final completion. Server startup, warmup and teardown are separate. This is warmed full-model serving performance, not deployment-total latency or sustainable capacity.

What happened to the earlier apparent gain?

In the preserved natural-stopping experiment, resident NuminaMath mean response was 10.65% lower than OFF while output tokens were 10.71% fewer (15,642 versus 17,519). Resident naturally stopped on fourteen requests versus eleven for OFF. Existing diagnostics show shared-prefix numerical differences followed by different generated sequences; placement, kernel shapes, batching or reduction order are plausible contributors, but the first cause is not isolated. This fixed-length control removes the earlier apparent advantage over OFF, supporting the interpretation that shorter answers drove that result. It is not an exact decomposition: forced continuation changes sequences, and the runs are separate episodes.

The same control retains a favorable response-time result versus ON on NuminaMath. The experiment does not distinguish savings from native history, dispatch, replication layout and control overhead. Resident jointly changes those mechanisms; OFF has 128 physical experts and ON/resident have 160. This is a comparison of complete configurations, not an isolated dispatch ablation. The activation backend remains all-gather/reduce-scatter; no sparse token-all-to-all serving claim is supported.

Limits and falsification

The hypothesized useful gain over OFF is not supported on either workload. The observed NuminaMath gain over ON survives matching per-request generation lengths. One group and one server episode per method cannot estimate run-to-run uncertainty: no confidence intervals, significance tests, request bootstrap or pooled overall effect are reported. Order was reversed relative to the previous study, not replicated within this one. Rates were preserved rather than retuned for forced output lengths. These results do not show that OFF is always best or that the method will help another arrival regime.

Native ON logs contain zero ordinary async launch entries for LongBench and three for NuminaMath across their entire server lifetimes, including warmup. These are not unique measured-phase cycles or verified commits. Native async drain, HTTP drain and absence of errors do not attest committed-weight consistency or migration payback. Prior resident weight and representative arithmetic checks are preserved; they do not certify full-model logits or answer quality. No further GPU experiment was added beyond the requested six sessions.
