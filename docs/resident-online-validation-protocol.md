# Online resident-dispatch validation amendment

This amendment is declared before measuring the online implementation. It leaves the completed headroom protocol, its archived source hashes, failed calibration attempt and revised successful pilot unchanged. The revised pilot on allocation 4869257 completed 80 rows and passed its frozen A/A screen: maximum cell deviation was 0.005319585. The precomputed `one_copy_home` mechanism advanced with block ratios 0.915803981 and 0.925515777; `token_balanced` stopped with 0.997970222 and 0.992478667. These are development measurements with selection cost excluded, not an online result.

The next implementation is one fixed, three-kernel GPU greedy algorithm with active-copy caps. It implements the selected concentration mechanism but approximates the CPU dynamic-programming assignment used for optimistic headroom. Do not claim that it produces the same assignments or achieves the same objective value. Logical top-k IDs, combining weights, fixed resident map, BF16 expert kernels and output collective remain unchanged. No new parameter grid or alternative policy is selected from this validation.

## Visible change to the development stop rule

The earlier protocol said to stop if the fully charged implementation could not meet the useful-performance margin on development data. The user's subsequent explicit request for a fresh test after successful headroom changes this one sequencing rule: **once the fixed online implementation passes correctness and execution-contract checks, run the already bounded fresh evaluation even if the charged development ratios miss 5%**.

This exception is recorded before online timing. It does not change the pilot's result, erase a development miss, relax the final 5% benefit or 2% regression criteria, or authorize tuning against fresh demand. Report development ratios in full. A fresh test conducted under this amendment is user-requested held-out evaluation; it is not described as having passed the superseded development-performance gate. If correctness or measurement integrity fails, do not advance on the strength of favorable runtimes.

## Thirty-two development runs

Use only the two existing pilot blocks, `opt-pilot-01` and `opt-pilot-02`, both captured domains (`domain0`, `domain1`), batches 128 and 1024, two reversed-order technical repetitions and two arms, `native` and `online`. This is eight input states and 32 completed rows. The online policy is fixed before these timings. The native arm uses native dispatch; the online arm computes its assignment from the current logical IDs on the GPU each forward. Neither uses future inputs to select a route.

Use exactly the revised setup contract: the original 16 conditioning input batches, every timing event recorded and synchronized before the timer, and 64 additional native SKIP conditioning calls with planning active. Cycle the 32 measurement input batches twice during that additional conditioning. Check unchanged weights/maps and zero transfers, then reset counters, observation windows/pass buffers, validity, decision logs, timing totals and terminal state. Run `gc.collect()` before the common synchronized start in both arms, with GC enabled during measured execution. Archive the excluded setup durations and input schedule.

Each measured trial cycles the 32 input batches eight times: 256 completed forwards and SKIP steps. Verify proposals at 63, 127 and 191, reject all weight migrations, and suppress the terminal proposal at 255. The primary measured duration is the maximum completed time across the two ranks. It includes all three selector kernels, histogram/assignment work, physical-ID production, recording, any required per-step input/assignment adaptation, expert execution, output all-reduce and native observation/planning. Static metadata preparation, compilation, common input materialization and declared conditioning remain excluded. An offline DP assignment must not substitute for the online selector inside this timer.

The cyclic workload is deliberately constructed from previously captured teacher-forced inputs. It is not an observed serving-demand stream. Cache conditioning and repeated inputs limit generalization and must be stated in the report.

## Descriptive analysis and diagnostics

The analysis plan is `configs/resident-online-validation-analysis-v1.json`, with CLI phase `paired_descriptive`. It requires all 32 keys and matched states. Average paired log online/native ratios across the two technical repetitions within each source-block/domain/batch cell, then exponentiate. Report all eight cell ratios, the four-cell geometric mean for each source block, equally weighted summaries for each batch and the overall eight-cell geometric mean. Retain individual paired times, order and allocation metadata.

There are **no confidence intervals, performance acceptance decision, parameter choice or selection from these two development blocks**. A ratio of 0.95 may be shown as a descriptive reference to the final practical target, but is not a confirmatory success. Missing, incorrect or incompatible runs are not silently dropped or imputed. The amended advancement prerequisite is a complete and independently audited implementation/correctness record, not a newly chosen development threshold.

Record approximation quality and selector cost separately. Compare the greedy and offline-DP assignments on exactly the same development inputs and resident map, reporting active-copy counts per rank, maximum active copies, token load per rank and actual padded work. Differences in legal physical assignment or a worse optimization objective are approximation loss, not changed logical model semantics. Verify logical-route preservation, count conservation, reconstructed logical windows, planner trajectory, zero transfers and unchanged maps/weights independently.

Selector cost needs directly measured diagnostic timing or a justified profiler range for its three kernels. Do not estimate it as online total time minus native total time, because assignments also change expert execution and rank/collective waiting. Keep any intrusive per-selector profiling separate from the primary unprofiled comparison. The completed online timer already charges actual selector overhead; do not add the headroom pilot's hypothetical 1% selector reserve to it again.

Check numerical outputs against native dispatch under the declared BF16/FP32 tolerances. State exactly which full input batches and which FP32 token positions were checked. Preserve all correctness failures and source fixes. A genuine correctness repair before source freeze is not permission for performance-driven parameter retuning; record its reason and revalidate the affected contract before any fresh test.

## Fresh evaluation remains fixed

After correctness validation, freeze the one online implementation, source and analysis hashes, allocation/order plan, fresh input provenance and all timer boundaries. Use eight fresh document blocks disjoint from development and prior studies, four regimes (`stable`, `transient`, `persistent`, `switching`), batches 128 and 1024, two arms and one paired repetition in each of two distinct allocation windows: **256 runs**. Preserve 32 input-history conditioning steps and 512 measured steps, and carry the revised initialization/conditioning safeguards into the final runner with their excluded costs explicitly logged.

The primary contrast and acceptance rule are unchanged. Average paired log online/native completed-runtime ratios over two allocation repetitions, then equally over the six changing regime/batch cells within each block. Resample the eight source blocks jointly with the frozen 20,000-draw, seed-10471 bootstrap. Useful gain passes only if the aggregate 95% upper endpoint is at most 0.95. The stable guard requires both stable batch cells' family-adjusted upper endpoints and the stable aggregate 95% upper endpoint to be at most 1.02. Both must pass for acceptance. Show each allocation separately; do not treat steps, ranks or technical repeats as additional workload samples.

The final interval remains conditional on eight selected document blocks, two allocation windows and a constructed replay. It does not establish population-wide serving performance. A negative fresh result is retained and reported under the original criteria; it does not trigger another policy or threshold search.
