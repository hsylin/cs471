# Bounded fused-MoE kernel optimization

This follow-up tests one engineering intervention: selecting a native BF16 fused-MoE tile configuration for the measured layer and hardware. It introduces no new placement objective, routing rule, predictor, or admission gate. Existing vLLM already supports configuration overrides and kernel tuning; the contribution is a measured improvement, if any, on this exact execution path. The pinned [fused-MoE source](https://github.com/vllm-project/vllm/blob/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/model_executor/layers/fused_moe/fused_moe.py) and [official tuner](https://github.com/vllm-project/vllm/blob/db9527a46873454610df6dbedf79a36d6bf1a7f6/benchmarks/kernels/benchmark_moe.py) establish this mechanism as existing functionality. A smaller M tile is a padding-efficiency hypothesis, not a conclusion about hardware bandwidth or compute saturation.

## Scope and fresh inputs

Retain pretrained Qwen3-30B-A3B layer 0, BF16 weights, 128 logical experts, top-8 routing, 160 physical slots, two H100s with NV6 connectivity, synchronous native EPLB, replicated inputs and output allreduce. Capture two fresh pilot and eight fresh final source-document pairs, disjoint by document identity and content from all earlier payback sources. Each pair contributes 2,048 teacher-forced causal-prefill token records from prose and 2,048 from Python source. Hidden states, logical expert IDs, and combining weights stay unchanged. These are constructed temporal replays, not natural online sessions.

Replay geometry is 32 common untimed observation inputs plus 512 measured steps, with a 16-step native window and 64-step rebalance cadence. Stable uses prose throughout; transient and persistent switch to code at measured step 120, with transient returning at 136; switching begins alternating 16-step phases at 112. Transient recurrence is 1,024, outside the measured horizon. The replay seed is 10471. Full tapes contain 544 inputs. Earlier studies remain immutable and are not pooled into the new estimates.

## Bounded pilot selection

The candidate table is fixed before timing: native `DEFAULT`; six configurations with `BLOCK_SIZE_M` in {16,32,64} and `BLOCK_SIZE_N` in {64,128}, all using K=64, group=1, split-K=1, four warps and three stages; plus M=128, N=64, K=64, group=1, split-K=1, eight warps and three stages. There are eight labeled options. At batch 128, one explicit option duplicates the default fallback; retain and label it as a null check, not an independent algorithm.

The tuner uses the shared initial physical map with no observation or migration. For each of two pilot blocks, two domains, and batches 128 and 1,024, measure each option three times: 192 trials, each containing 32 complete forwards on varying captured positions. Inputs and initial map are identical across options within a cell/repetition. Compilation, materialization, correctness checks, and common warm-up are excluded from timing and logged separately. Configurations and repetition order are balanced and randomized without using outcomes. Measure completed forward time including physical mapping, expert work, and output allreduce; do not select by isolated GEMM duration.

For each batch, average paired log candidate/default durations over the three technical repetitions within each block/domain cell, then give the four cells equal weight. A candidate is eligible only if all required trials are complete and numerically correct and no cell's paired geometric mean ratio exceeds 1.02. Choose the eligible candidate with the lowest aggregate ratio. If default is within 1% of the fastest eligible option, choose default. Break any remaining numerical ties by the frozen candidate-table order. Selection is per batch only, shared across domains, regimes, blocks, and policies. The duplicate default option cannot create additional independent evidence.

Freeze the selection output and its input hashes. Then run a full-policy pilot validation with the selected configuration and default, crossed with B3 and SKIP: two blocks × four regimes × two batches × four arms × one repetition = 64 runs. This is a check of the selected setting under the actual policy trajectory; it does not reopen the grid or choose a different candidate if timing is unfavorable. Correctness or implementation failure can block execution, but any correction must be documented and provenance frozen again before final timing. No extra configuration search is allowed.

## Final factorial comparison

The final design has eight unseen blocks, four regimes, two batches, two technical repetitions, and four arms: DEFAULT+B3, TUNED+B3, DEFAULT+SKIP, TUNED+SKIP. Total: 512 complete policy runs. All four arms within a block/regime/batch/repetition form a matched group with balanced execution order. The selected per-batch configuration is fixed before final measurements. If tuning selected default, TUNED is an explicitly labeled duplicate-control arm, not a hidden alternate implementation.

Each arm starts from the same verified weights and physical map. B3 includes native observation, planner, admission and accepted transfer/commit during timing; SKIP keeps its declared policy behavior and matching instrumentation. Kernel changes must preserve exact logical routing, native physical observation counts, and the sequence of accepted maps and moves for a fixed policy. Record and compare a decision-trajectory hash across DEFAULT/TUNED within each policy; compare initial-state, input and weight hashes across all four arms. Output differences must satisfy the fixed numerical contract. Any differing policy trajectory invalidates attribution to a kernel-only intervention until explained.

The primary timer covers 512 completed measured steps and final device synchronization. The 32 observation inputs are untimed; initialization, JIT compilation, all-step input materialization, output checks and post-run audits are excluded and their costs recorded. There is no claim about input-copy latency, cold-start latency, or end-to-end serving. A scheduled proposal after the last measured forward is suppressed because it cannot affect any measured future, consistently across all arms. Record actual monitored steps, decisions, bytes, and complete mapping/weight checks. Restore the process-global kernel override after each trial, including exceptions; verify the installed override and actual resolved configuration.

## Outcomes and uncertainty

The primary contrast is TUNED+B3 / DEFAULT+B3, aggregated with equal weights across six changing regime/batch cells. Useful gain requires ratio ≤0.95. Stable regression requires ratio ≤1.02 in both stable batch cells and the stable aggregate. TUNED+SKIP / DEFAULT+SKIP is a separately declared secondary mechanism control showing whether the change benefits the forward path with migration suppressed. B3/SKIP comparisons and the ratio of the two kernel effects may be reported descriptively; they do not establish a new balancing-policy contribution.

Average paired log ratios across the two technical repetitions before resampling. Resample all eight source blocks as shared blocks across cells, using 20,000 percentile-bootstrap draws and seed 10471. Ordinary 95% intervals apply to each aggregate. For cell-level claims, use Bonferroni-adjusted percentile endpoints across six changing cells or two stable cells, separately for the B3 primary and SKIP secondary contrasts. These are declared endpoint families, not one simultaneous interval over every number. A criterion passes when the relevant upper endpoint meets the margin, fails when its lower endpoint exceeds it, and is inconclusive otherwise. Failure to establish a 5% useful gain does not by itself establish slowdown.

The eight hand-selected document pairs are finite-corpus resampling units. Disjointness is checked but does not establish independence in a production workload population; the files share projects and possibly authors. Repeated timings are not new source blocks. One allocation does not estimate hardware-day variation. Report complete-cell intervals only with all eight blocks, and give every invalid/missing group and failure. Incomplete matrices cannot produce a confirmatory pass. No final-data retuning, regime selection, candidate replacement, optional stopping, extra horizon, or enlarged grid is permitted.

The completed outcome may be a useful speedup, an inconclusive effect, or a negative engineering result. A positive effect should be called kernel-configuration optimization on this layer and execution path. It is not a new MoE routing or load-balancing algorithm, and it does not revise the earlier frozen payback or TV results.
