# Serving evidence and workload generalization

The strongest remaining test is whether the measured improvement survives changes in arrival structure and routed content, while preserving the native control path and the incremental comparison against the shortcut alone. The existing three-arm design can separate those mechanisms. A larger collection of synthetic calendar seeds would chiefly refine uncertainty within the present workload generator. Production timestamps and fresh semantic inputs test a different limitation. The serving literature supports that distinction: several influential evaluations combine real request lengths with newly generated arrival times, whereas the newer public trace releases expose actual arrival calendars. [PagedAttention](https://doi.org/10.1145/3600006.3613165), [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal), [DynamoLLM](https://doi.org/10.1109/HPCA61900.2025.00102), [BurstGPT](https://doi.org/10.1145/3711896.3737413).

## Workload evidence

A trace is not a single kind of evidence. It may supply only arrival counts, token lengths, complete timestamps, semantic prompts, or some combination. InferLine preserves a generated trace across compared systems and separates profiling from evaluation draws, but its real-derived experiment reconstructs sub-minute arrivals from aggregate rates. AlpaServe fits and resamples Gamma arrivals from Azure Functions workloads. INFaaS uses Twitter activity as a proxy. These are useful controlled experiments; none makes the generated schedule an observed LLM request sequence. For this project, transformation rules should therefore be part of the estimand: which rows were selected, whether times were scaled, which fields were preserved, and what one replayed job represents. [InferLine](https://doi.org/10.1145/3419111.3421285), [AlpaServe](https://www.usenix.org/conference/osdi23/presentation/li-zhouhan), [INFaaS](https://www.usenix.org/conference/atc21/presentation/romero).

Real token lengths do not by themselves validate real temporal demand. Orca uses synthetic lengths and Poisson arrivals; vLLM and Sarathi-Serve use natural-workload lengths with Poisson timestamps; Llumnix varies Poisson/Gamma arrivals with several length families. These designs help isolate capacity, burst sensitivity and scheduling mechanisms. They do not test the joint distribution of temporal demand, prompt content and expert routing. The relevant extension is to preserve a new calendar's relative timing and use authentic fresh layer-zero captures, without treating a fixed token batch as a complete conversational request. [Orca](https://www.usenix.org/conference/osdi22/presentation/yu), [PagedAttention](https://doi.org/10.1145/3600006.3613165), [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal), [Llumnix](https://www.usenix.org/conference/osdi24/presentation/sun-biao).

Public Azure traces offer a stronger temporal test while leaving content dependence unresolved. Splitwise's public trace lineage contains invocation times and token counts; its capacity simulation nonetheless resamples Poisson arrivals. DynamoLLM supplies the later Azure release and explicitly separates physical cluster measurements from week-scale simulation. The dataset publishes no prompt text. Its documentation's assertion that text does not affect the profiled performance cannot be transferred to a routed MoE layer. A defensible extension combines independently sourced text captures and trace-derived layer-job calendars, and states that the original correlation between customer content and arrival time is unavailable. [Splitwise](https://doi.org/10.1109/ISCA59077.2024.00019), [DynamoLLM](https://doi.org/10.1109/HPCA61900.2025.00102), [Azure2024 metadata](https://github.com/Azure/AzurePublicDataset/blob/215becdacba1ce682c7368642ce97d5a332de7a6/AzureLLMInferenceDataset2024.md).

The downloaded files, rather than dataset prose, must define the sampling frame. The parent audit found that Azure2023's small current CSVs have dates inconsistent with its introductory description; Azure2024 offers more days for separated development and test windows. Selection should record actual file hashes, dates, row boundaries and timestamp resolution before measuring either treatment. Days from the same public service are temporal strata, not independent production deployments. Content blocks, calendar dates and repeated measurements are different sources of variation; repeating a run or extracting several windows from a day does not create more independent days.

## Mechanism and measurement

End-to-end improvement need not follow the fastest individual kernel. PagedAttention reports a slower attention microkernel alongside better serving capacity because memory management changes the effective batch. FlexGen reports high-throughput offline execution under large batches and offload; its overlap-disabled breakdown is not an additive description of the overlapped critical path. DistServe separates time-to-first-token from token-generation latency and constrains both. These results support retaining complete arrival-to-completion time, observed service time and queueing separately, rather than projecting system gain from expert counts or isolated CUDA durations. [PagedAttention](https://doi.org/10.1145/3600006.3613165), [FlexGen](https://proceedings.mlr.press/v202/sheng23a.html), [DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin).

Control-path equivalence remains essential when interpreting a small optimization. InferLine and INFaaS deliberately share serving infrastructure across policy comparisons. Clockwork counts admission and rejection explicitly and distinguishes real worker experiments from controller emulation. For this study, the same logical routes, native observations, calendars and completion coordinator should be exercised across native, shortcut and combined arms. Physical assignments may differ for the resident dispatcher, so their correctness requires a separate mapping oracle. A faster combined/native comparison alone cannot identify the dispatcher contribution; combined/shortcut remains the decisive incremental contrast. [InferLine](https://doi.org/10.1145/3419111.3421285), [INFaaS](https://www.usenix.org/conference/atc21/presentation/romero), [Clockwork](https://www.usenix.org/conference/osdi20/presentation/gujarati).

Workload structure also determines which improvement is available. Parrot and SGLang exploit dependencies, prefixes and constrained programs that do not exist in an isolated layer replay. MuxServe exploits multi-model contention, and its synthetic maxima exceed its real-trace gains. VTC shows why aggregate throughput can conceal unequal service. These papers motivate fresh content families and retained subgroup safeguards; they do not justify expanding this project into a full agent server or predicting its token throughput from layer-job response. The carried-forward 5% useful-gain and 2% regression margins are engineering decisions, not constants established by this literature. [Parrot](https://www.usenix.org/conference/osdi24/presentation/lin-chaofan), [SGLang](https://doi.org/10.52202/079017-2000), [MuxServe](https://proceedings.mlr.press/v235/duan24a.html), [VTC](https://www.usenix.org/conference/osdi24/presentation/sheng).

## Artifact and inference limits

A published artifact still needs a timing-contract audit. In BurstGPT's current example at commit `d895a53`, the CSV loader converts timestamps into successive gaps, while the runner creates tasks concurrently and sleeps each task by its gap. A three-row calendar at offsets 0, 1 and 2 consequently becomes sleeps of 0, 1 and 1. This is a static finding about that example revision, not evidence that the KDD evaluation used it. Reusing the raw data with the project's absolute-clock replayer is preferable to adopting this example unchanged. BurstGPT also distributes raw and cleaned releases; zero-output failures and full-response elapsed times must not silently become successful requests or TTFT measurements. [Pinned loader](https://github.com/HPMLL/BurstGPT/blob/d895a53bb7b8ec137d0d2fe203b335835a78c10a/example/src/burstgpt/workload.py#L82-L93), [pinned runner](https://github.com/HPMLL/BurstGPT/blob/d895a53bb7b8ec137d0d2fe203b335835a78c10a/example/src/burstgpt/runner.py#L48-L60), [BurstGPT](https://doi.org/10.1145/3711896.3737413).

The reviewed speedups are heterogeneous evidence, not a pool of replications of this project. Some are physical experiments, some simulator outputs, some offline throughput, and some application completion measurements. Request p99s describe a response distribution; they do not quantify uncertainty across workloads or hardware allocations. Several papers do not specify an independent-run confidence interval in the inspected sections. This does not mean they omit all repetition: DynamoLLM averages five 30-second energy-characterization measurements, separately from its longer cluster experiments. Those repetitions do not establish uncertainty across independent workloads. [DynamoLLM](https://doi.org/10.1109/HPCA61900.2025.00102). The project should retain its stronger separation of development and confirmation, publish paired per-block effects, and bound inference to the sampled content and calendars on the tested machine. With few unique dates, temporal robustness should be shown directly rather than hidden behind hundreds of jobs or bootstrap draws.

The smallest decisive next evaluation keeps the two H100s, one Qwen layer, fixed replica budget and three arms, while crossing prespecified fresh content blocks with trace windows selected without performance feedback. Raw timestamp preservation, independently verified releases, per-window queue conservation and numerical route/weight checks are the external correctness tests. A favorable result would support generalization to this finite collection of trace-derived layer workloads. Claims about actual chat-request TTFT, full-model generation, dynamic batching, new accelerator families or unseen production organizations would remain untested.
