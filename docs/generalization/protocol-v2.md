# Generalization inference amendment

This amendment is frozen before any new treatment timing. It supersedes the arrival-date assignment and statistical paragraphs of `protocol-v1.md`; content selection, capture computation, B128, fixed initial map, 32 extra replicas, two reserved H100s, three arms, charged timing boundary and correctness contract remain as specified there. The operative source selection is content-v2: it adds the same near-duplicate filter to decoded model-visible first512-token prefixes before splitting. An independent audit rejected three near-prefix pairs in content-v1, including one pilot/final pair. Content-v1 captures are ineligible for performance evidence; no treatment timing preceded this correction. Earlier results and protocols remain immutable. ## Scope and corrected sampling frame

The downloaded Azure2024 code file contains May10–16,2024; conversation contains May12–18. Each contains seven dates, despite the broader date range in the introductory README. Code pilot dates are May10–11 and final dates May12–16. Conversation pilot dates are May12–13 and final dates May14–18. The final union is **seven actual calendar dates, May12–18**, with May14–16 shared across services. Conversation pilot dates overlap code final dates. This is a within-service temporal split, not a global future-date holdout.

The source selector keeps three hash-ranked nonoverlapping 256-job blocks per pilot date and eight per final date. Each block also consumes a distinct following boundary row. This yields12 pilot and80 final candidate blocks. It does not create80 independent days. No timestamp sorting, burstiness filtering, favorable-performance selection or silent replacement is permitted. Source request lengths remain metadata; one source timestamp releases one preassembled B128 layer invocation.

The first version promised to account for calendar dependence through resampling without resolving the small, partially overlapping date structure. That promise is corrected here before timing. Primary intervals condition on the selected external trace material and describe content-bundle variation under the declared construction. They do **not** estimate uncertainty over new production days, services, organizations, arrival processes or GPU allocations. Date deletion supplies a separate finite-design sensitivity check, without a confidence interval. Shared calendar dates across services are always deleted together.

The implemented job constructor supersedes v1's cycle-traversal description: seed471503 derives a separate PCG64 full-bank permutation for each of272 raw jobs, selecting128 distinct records without replacement within each job. It rejects repeated unordered job combinations. Sixteen jobs are warm-up material and256 are measured; captured records may recur across jobs. Every index, prompt position and reuse count is archived. This tests constructed token groups from authentic captures, not naturally batched requests. Preparation/materialization/reference durations and conditioning durations are separately recorded as excluded setup; online selection stays inside charged service.

## Assignment and planning

The final allocation is six or eight content groups per dataset. Pilot comprises two groups per dataset. Each group receives one code block and one conversation block, each executed under calibrated and common rates with native, shortcut and combined arms. Treatment counts are72 pilot and216 or288 final. The24 diagnostic trials remain separate, giving at most384 treatment/diagnostic trials in total. Native-only capacity calibrations are additional and are not primary statistical units. No technical repeats are introduced.

`generalization/inference.py` defines deterministic assignment using seed471513. Dataset order is `gsm8k,mbpp,wildchat`. Group IDs within each dataset are ranked by SHA256 of the pipe-separated tuple `(seed,"assignment",phase,dataset,id)`; an ID tie is resolved lexically. For dataset index d, ranked group index j and n groups per dataset, the selected service date index is `(j+d*n+rotation) mod D`, where dates are chronological, D=2 for pilot or5 for final, and rotations are0 for code and2 for conversation. Pilot uses the selector's declared dataset-specific candidate on that date. Final uses the next unused candidate in source hash-rank order for that service/date. Blocks are never reused between content groups. Both rates and all three arms share the assigned block.

This produces final date counts of5,5,5,5,4 per service when n=8, up to service rotation, or4,4,4,3,3 when n=6. Each dataset has counts differing by at most one across all five dates. Source rows and dates remain part of every paired statistical record. Arm order uses all six permutations in balanced blocks, frozen before treatment timing. Assignment consumes no route, architecture, latency or treatment-outcome field.

The pilot planning rule is retained exactly as a limited precision heuristic. For each of the six pilot content groups, average the four combined/shortcut log mean-response ratios across arrival type and rate definition. Let s be their ordinary sample standard deviation with denominator5. Compute `2.571*s/sqrt(18)`. Choose six final groups per dataset only if this quantity is at most0.03; otherwise choose eight. Report each dataset's two-group sample SD and both projected widths. The coefficient2.571 and0.03 log-ratio width were specified in v1. This is not a power calculation or a guarantee about the seven guarded intervals; six pilot bundles cannot establish unseen temporal variance. The apparent mean benefit is not a decision input. Uniformly shifting every pilot log effect leaves the allocation unchanged.

If six groups are selected, choose them from the eight preselected groups per dataset by SHA256 rank of `(471513,"select",dataset,id)`, before any final timing or final routing inspection for optimization. Do not choose groups by capture length, route distribution, expected benefit or timing. The final manifest records the selected IDs, dates, blocks, exact schedules, order, source hashes, inference code hash and chosen n before execution.

## Endpoints and uncertainty

For content group g, arrival type t and rate r, the run-level paired log ratio is `L[g,t,r]=log(mean_response_combined/mean_response_shortcut)`. Mean response includes every released job through completion under the preserved absolute calendar. Each group score is the arithmetic mean of its two arrival-type log ratios. The reported ratio is the exponential of the equal-weight mean of dataset means of group scores. Thus no long trace, slower workload or large token count receives extra statistical weight. Per-trial p95 uses the frozen finite-sample quantile convention before a paired ratio is formed; jobs are never bootstrap observations.

The primary endpoint is combined/shortcut mean response under native-calibrated0.85load. Draw100,000 bootstrap samples with NumPy `default_rng`/PCG64 seed471512. In fixed dataset order, independently draw n group indices with replacement within each dataset, producing one `(100000,n)` index array per dataset. Use those same three arrays for every endpoint and contrast. Resample the **whole content bundle**, retaining both arrival types, both rate definitions, all arms, every nested job and their observed dates. Use NumPy linear quantiles. The primary two-sided95% percentile interval must have upper bound **strictly below0.95**.

Seven shortcut-relative guards retain the v1 family: mean response for each of three datasets under each of two rate definitions, plus aggregate calibrated-rate p95 response. Each uses a one-sided percentile upper bound at `1−0.05/7 = 0.992857142857…`; each upper bound must be at most1.02. Dataset guards use their corresponding stratum's shared draw array. The primary cannot be replaced by the common-rate result, and a guarded dataset cannot be dropped. These are conditional bootstrap intervals with a small number of constructed content groups, not a claim of exact finite-sample coverage or production-population generality.

For every date in the actual final union, delete all code and conversation cells bearing that date, including both rate definitions and all treatment arms. For the robustness endpoint, recompute combined/shortcut calibrated mean response: average surviving arrival types within each group, surviving groups within each dataset, then the three datasets equally. A group with no surviving type is omitted; a deletion leaving any dataset empty is not estimable and fails the robustness requirement. Report retained groups, deleted bundles, all seven point ratios and their minimum/maximum. **Every deletion's point ratio must be at most1.02.** This tests whether removal of a date exposes aggregate regression. It does not require a fresh5% gain in each smaller subset and is not an eighth inferential confidence guard.

Incremental acceptance requires the primary, all seven interval guards and all date-deletion point checks. Only then is combined/native calibrated mean response tested as a hierarchical secondary endpoint, using the same95% interval and strict0.95 upper-bound requirement. If the gate is closed, report only its point ratio and label the secondary `not_tested_gate_closed`. Overall acceptance additionally requires that secondary. Shortcut/native and all dataset/type/rate cell ratios are descriptive. No unregistered cell-level intervals or significance tests are added.

## Interpretation and failure

The revised design asks whether the incremental dispatcher benefit persists across the declared fresh content construction within this finite external-trace evaluation domain. Its bootstrap does not identify separate content and calendar variance components. Multiple windows from a day are nested design material, and their counts cannot justify a new-day claim. The leave-one-date-out range describes sensitivity within this span, not future temporal robustness. The fixed-content/calendar pairing also cannot recover the absent correlation between actual Azure customer text and arrivals.

An upper bound at or above0.95 fails to establish useful incremental gain. A guard upper bound above1.02 leaves the regression safeguard unestablished; it does not prove harm. Date-deletion point failure prevents the preregistered robustness claim but is not a statistical finding about future days. Any structural, numerical, source-hash, route, calendar, conservation, map or completion failure invalidates that run and the complete-matrix acceptance result. Report failures rather than silently replacing a case. All architectural and timing associations remain descriptive unless separately controlled.
