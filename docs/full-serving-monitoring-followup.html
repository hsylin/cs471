Latency diagnosis and cheaper B3/B4 monitoring

Status: development and diagnostics; final performance not measured. This follow-up preserves the prior negative results and tests one engineering change: fusing physical-to-logical count maintenance and directly reducing the two windows without copying the whole ring into chronological order.

The model, eight H100s, DP8/TP1/EP8 AgRs backend, two datasets, one group, arrivals and per-request output targets stay fixed. LongBench produces 162 tokens per arm; NuminaMath produces 17,519. This reuses previously examined inputs and does not establish fresh-content generalization. Equal lengths do not imply identical generated tokens, routes or answer quality.

Latency diagnostic

Separate instrumented sessions compare OFF, resident_v2 and original B3 on both datasets. An opt-in ASGI middleware records request receipt, render boundaries, engine submission, selected DP engine, first engine output and stream delivery, plus API event-loop lag. Records contain timestamps and opaque identifiers, never prompt text, output text or token arrays. These sessions are diagnostics, not final uninstrumented speed measurements. First engine output is not necessarily first text content. API spans share one monotonic clock; cross-process/client comparisons require verified host alignment.

The failed initial attempt exposed custom plugin metadata to OFF during diagnostic startup. It served no requests. The next deployment exposes only the repository root for the native middleware; custom bootstrap metadata remains isolated to custom arms. Failed artifacts are preserved.

Policy-preserving monitoring change

The original proposal_gate_plugin.py remains unchanged. Optimized arms use monitoring_gate_plugin.py and the same pure decide function. Both retain continuous recording, 1,000-step windows, 5% gain, 5% TV, 3,000-step native interval, native candidate generation, rank agreement, transfer handling and normal commit-event observations.

A single GPU kernel owns each layer's ring row, zeroes it and accumulates physical-copy counts into logical experts under the pre-commit map. Dummy steps remain zero and advance the same clock. A separate direct-reduction kernel snapshots the two consecutive windows at arbitrary offsets into independent output storage. It avoids the original full-ring index_select allocation and the per-step conversion/masking/casting launches. All history operations and logging remain charged.

An attempted rolling-sum candidate failed the exact GPU oracle after repeated wraps at step 3749: its ring and current-window sum were correct but its previous-window sum drifted. It is excluded, with failure records retained. No incorrect candidate can enter a serving comparison. The simpler direct-reduction candidate must pass an independent NumPy oracle, charged component timing and full-model all-rank shadow comparison against the original history before admission.

Frozen final comparison

The planned uninstrumented final has nine configurations on each dataset: OFF, B1, B2, original B3, original B4, resident_v1, resident_v2, B3-light and B4-light. This is eighteen sessions, one group per dataset. The original seven configurations are contemporaneous controls. The original dispatcher policies, replica budget and placement are untouched.

Primary comparisons are B3-light/B3, B4-light/B4 and each optimized gate versus OFF. Report mean/p95 full response, TTFT, native phase durations, completed elapsed time and drain, throughput, token counts, decisions and observed completed/censored commits. A lower byte count or faster counter kernel is not a serving speedup. A 5% useful mean gain and 2% workload-regression guard remain decision margins; one group supports descriptive ratios only, not confidence intervals or significance.

Final admission requires exact output lengths and no failed requests, fixed input/calendar/source manifests, native runtime checks and all-eight-rank shadow equality during pilots. Completion requires stable remote/local raw-file inventories, Git source hashes, independent arithmetic and a fresh reconstruction. Async draining is not commit proof. Missing event completion remains censored; event completion alone does not prove final full-weight contents.

Scope boundaries

No TV/gain tuning, new placement, learned predictor, transport replacement or model-precision change is part of this intervention. Request-path fixes will only be considered if the diagnostic supports a concrete cause; the unexplained earlier latency residual is not by itself evidence of a CPU, GIL, JIT or network defect. Pilot profiling includes the expensive reference shadow and is not a production-cost measurement. Profiling and correctness instrumentation are disabled in final timing sessions.
