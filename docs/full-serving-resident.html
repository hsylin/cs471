Full-model resident dispatch

The method chooses which already loaded expert copy handles a token. It now runs inside the complete Qwen3 model, so each measured request includes prompt processing, all 48 MoE layers, generated decoding, and HTTP streaming. Whether this improves response time is an experimental question; this page explains the implementation and the reproduction procedure.

Evidence snapshot, 10 November 2026: the GPU mapping gate and first loaded-weight/probe audit passed, and the correctness-only server completed 40 pilot requests. Timed pilot admission and the held-out comparison are separate gates. This document contains no final speedup result; the generated comparison report is the authority for measured final results.

One fixed map; one chosen copy per active expert

Each layer has 128 logical experts, with eight selected for each token. Native EPLB OFF stores 128 physical expert slots, 16 per GPU. Native EPLB ON and our method have the same budget of 160 slots: 128 originals plus 32 extra copies, or 20 slots per GPU. OFF therefore has a smaller expert-storage footprint; the three-arm comparison deliberately retains this native difference.

Our map is independent of the test data. Rank r owns experts 16r…16r+15 and four extra experts from its partner r XOR 1. The pairs are (0,1), (2,3), (4,5), and (6,7). For example:

At each MoE execution, the resident dispatcher counts the already gathered logical assignments. It assigns each active duplicated expert to one of its two resident copies for that invocation. Within each pair, it handles the largest token counts first and prefers the less-loaded eligible rank, subject to an active-expert-count cap. Experts without a copy stay on their owning rank. Choosing one copy can reduce the number of active physical experts and padded expert work, but can also concentrate tokens and costs extra GPU work. The policy makes no runtime-optimality claim.

The CPU oracle and dispatch wrapper and Triton kernels preserve logical expert identity, combining weights, and native -1 padding. Small routing arrays use one fused kernel; larger arrays use histogram, planning, and application kernels. There is no additional collective or CPU tensor read in this online mapping path. All mapping overhead is included in request timing.

Where it is inserted, and what stays native

The opt-in adapter binds exactly 48 native MoERunner instances. In resident_v1, it replaces physical-copy selection immediately after native MoEPrepareAndFinalizeNaiveDPEPModular.prepare gathers logical routing IDs. The gathered hidden states, routing weights and padding remain native. Native Triton expert arithmetic, attention, KV-cache management, scheduling, sampling and HTTP serving remain in use.

Activation communication uses vLLM's allgather_reducescatter backend, logged as AgRs. This is not an experiment with an optimized token all-to-all backend. Native EPLB ON uses the recorded TorchDistGlooStagedEplbCommunicator for expert-weight transport; this is a different operation from activation exchange.

What has been checked

The kernel gate covers 44 shape/dtype/mode cases, including padding and graph replay. The first loaded-weight audit records all eight ranks and 48 layers: 7,680 physical layer-expert instances, 6,144 logical instances, and 1,536 duplicated instances. Full BF16 replica hashes agree. These are loaded-tensor identity checks, not an independently recomputed copy of every checkpoint tensor.

Startup probes execute real loaded expert weights at layers 0, 23 and 47 using distinct rank inputs, heterogeneous padding and an all-padding case. Logical identity, token conservation, combining weights, CPU-oracle selection and gathered-rank agreement pass. Native expert outputs and a direct FP32 reference pass the predeclared elementwise bound abs(error) ≤ 0.02 + 0.03 × abs(reference); the maximum native-reference absolute difference was 0.0625, so “passed” does not mean bitwise equality. The correctness-only server also completed eight authentic pilot requests per dataset, 40 total, with finite diagnostic logprobs and matching prompt/token metadata.

These checks do not prove every full-model logit or answer is equivalent. Normal EOS can produce different output lengths, even with temperature zero. Probe instrumentation must be disabled in timing configurations. The pilot admission requires correctness and complete finite timed OFF/resident/placement-only runs; it does not require a win over OFF. A correct negative result remains admissible.

The held-out comparison

The public protocol reserves WildChat, ShareGPT, InstructCoder, NuminaMath and LongBench separately. Each contributes 64 held-out inputs, divided into four disjoint 16-request blocks. Each block runs OFF, ON and resident on fresh servers: 60 server sessions and 960 measured executions. Each server first runs the same eight pilot warmups twice, for another 960 warmup executions. Pass one requests diagnostic IDs/logprobs; pass two uses ordinary payloads.

Messages are not truncated to 512 tokens. The context limit is 32,768 tokens and generation is capped at 2,048 new tokens, with non-thinking chat formatting, temperature zero and normal EOS. Each block shares its exact absolute calendar across all three arms. Azure code/conversation timestamp blocks are scaled once to the previously fixed per-source pilot rate; relative spacing and ties survive, but this is not the original production rate or an authentic joint sample of content and arrivals. All admitted requests drain, including overload cases. Arm order is explicitly balanced; rates, maps and input selection cannot be tuned from final outcomes.

The primary endpoint is response time from scheduled arrival to completed response, resident versus OFF; resident versus ON is secondary. The report keeps mean/p95 response, TTFT, episode elapsed, drain, request throughput, output throughput and generated lengths separate. Completed elapsed includes the offered horizon and drain. Startup, warmup and shutdown are reported separately, outside warmed episode timing. Native queue/RUNNING metrics retain exact engine labels; RUNNING is not GPU kernel service.

There are only four independent content/arrival blocks per source. Equal-block geometric mean ratios and pointwise Student-t intervals on paired log ratios are exploratory. A 5% useful-gain point margin and 2% regression point margin do not establish a confirmatory guarantee. There is no request bootstrap, cross-source pooling, or automatic superiority claim. Missing or invalid triples withhold their contrasts and four-block summaries. Native ON can adapt during warmup; ordinary launch logs and drained asynchronous work do not prove normal commit completion.

Reproduce without changing the evidence

The archived experiment uses frozen-v2/protocol.json. The first freeze was superseded before execution solely to include a late shutdown-log tail; inputs, method and analysis are unchanged. Run the following reproduction commands from the repository root with its pinned environment, using fresh output paths. The private input bundle remains outside Git; the public source manifests and prior tokenizer admission bind its content. The freeze command only materializes the reserved inputs after a passed pilot gate; it runs no model inference. Output paths must be new.

Completion and the speedup interpretation

The experiment continues independently on the cluster. Reporting must wait for the controller wrapper to write controller_exit=0, all 60 sessions to close, and the raw logs to stop changing. Two identical SHA-256 inventories taken on the cluster around the last transfer must match the local files exactly. The closure helper also checks all recorded controller source files against the declared Git commit. A separate statistics implementation reconstructs responses, elapsed time, output counts and four-block intervals directly from the public records. Neither HTTP completion nor this file audit attests a normal native asynchronous EPLB commit.

The HTML report explains both comparisons separately for each dataset. It distinguishes a lower observed full-response time from an equal-generated-work speedup, shows when uncertainty includes no change, and retains p95 or completed-elapsed regressions. Different answer hashes or token totals remain visible even if the mean looks favorable. The 5% useful-gain and 2% regression margins are the frozen point-estimate criteria, not new hypothesis tests. A four-block result never becomes a universal production-capacity or semantic-quality claim.
