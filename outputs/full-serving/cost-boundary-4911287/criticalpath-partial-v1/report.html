哪些解釋已被削弱？

「大量不變映射更新就是主要瓶頸」沒有獲得正式比較支持。不變映射確實提供可省略提交的機會，正確性也已驗證；但機會數與 CPU 呼叫耗時不等於位於關鍵路徑的可省時間，最終收益未達 5%。

「每次 readiness 等待都讓整機停擺」不符合目前的 trace。B4 proposal 視窗配對出 88 次八 rank 檢查，25 次就緒、63 次未就緒。只有 4 次在保守時鐘區間下，存在八個主執行緒同在 readiness 內、且所有 trace 都沒有觀測到 CUDA 活動的時段。這不是所有暴露成本的上限，也不排除局部等待。

「NCCL kernel 很長，所以網路頻寬就是瓶頸」不能由這份資料推出。OFF、B4 都有跨 rank collective 到達時間分散。配對採用相同名稱與順序的假設，缺乏 transport sequence ID；持續時間可能包含等待其他 rank，不能直接換算傳輸成本或頻寬。

OFF 含四個一般視窗，B4 另含 proposal 視窗；兩列不是等量樣本或處理效果比較。事件跨層、跨請求相依，不能當成獨立重複實驗。kernel 名稱分類僅是候選分類；缺少前置工作不代表沒有前置工作。

多數晚到事件無法只靠同 stream 順序還原依賴。以檢查過的 OFF late rank 2 trace 為例，事件等待與記錄 API 有呼叫 correlation，卻未提供可連結 record／wait 的 CUDA event 身分；因此不能聲稱已重建完整跨 stream 關鍵路徑。

哪些仍未釐清？

同一物理配置、同一路由規則的 fixed_idle／fixed_charged 主對照尚未完成，因此仍不能將管理成本與動態路由效果分離。現有 static／resident 對照改變路由規則，也不足以補上這個缺口。

八 rank 的實際工作不均、attention 工作量代理值與 collective 晚到現象已被觀測到；但仍需沿同一 stream 的前置工作與 CPU／CUDA 順序，確認誰阻止下一步。kernel 時間加總、代理值最大、或晚到 rank 本身，都不是因果證明。

proposal trace 只涵蓋 48 層中的前 25 層提交；完整事件紀錄確認所有層最終提交，不代表後半段的關鍵路徑已被捕捉。NuminaMath 尚無這次主診斷資料。

為什麼修正後仍可能慢於 OFF？

修正保留了 B4 的記錄、歷史統計、planner、worker、readiness、傳輸與事件回收流程，只省略精確不變映射的逆向映射提交。B4 與 OFF 的配置及路由行為也不同。因此省去一項工作，不保證消除其餘成本，更不保證配置收益足以抵銷成本；目前不能將 4.597%／5.608% 的殘餘差距拆成可信的因果百分比。

下一步的選擇

最值得先做的是小範圍診斷方法驗證：確認多次捕捉與 CUDA graph 共存的穩定性，並取得可連結跨 stream record／wait 的事件身分。方法驗證通過後，再補齊同配置、同路由的控制。現階段不建議再刪 readiness、改 admission 門檻，或把另一輪相同正式效能比較當作歸因證據。
