全模型：一次改一個因素

每個 pilot 為 16 warmup＋8 probe，來源與合約在執行前固定。120 個請求逐筆重查，共 102 成功、18 失敗；僅重算成功請求的 mean／p95 response 與 TTFT 來核對檔案，沒有用它們做效能比較。第一列對照先前啟用 sync activity 的 charged 設定；第二列以第一列為基準。最後三列各自以第二列為共同基準，分別只關閉 graph、改輸出等待位置或關閉 external correlation，沒有把三個因素累加。CPU 切片效能修正位於捕捉之後，且已核對事件選取完全相同。

「關閉 graph」只設定模型 cudagraph_mode=NONE，沒有使用同時停用編譯的 enforce-eager。模型與非同步輸出、B4 worker 仍在；但 graph 模式也會改變記憶體需求與排程，因此結果不是單一底層 kernel 或驅動缺陷的因果證明。其餘 CUDA 失敗均記錄到 Xid 13；graph 關閉案例在檢查區間未新增 Xid。

現在能排除哪些過度簡化的解釋

  • 移除中間窗口邊界仍失敗，因此不能只歸因於反覆開始／結束或中間 barrier。
  • 關閉 native sync activity、external correlation 各自仍失敗，兩者都不是單獨足夠的修復。
  • 把既有 copy-event 等待移到輸出產生端後，錯誤改在該處回報。僅由背景輸出執行緒的等待方式，無法完整解釋現象；錯誤回報處仍不等於出錯 kernel。
  • 單窗口與輸出等待兩個失敗案例，八 rank 的 48 層 commit 都在捕捉前約 5–7 秒完成。沒有觀測到捕捉期間的新提案／commit；不能直接稱為正在搬權重造成失敗。這不證明 worker 已完全靜止，也不排除先前狀態、history 或 readiness 的影響。

小型案例比上一輪更接近了什麼

先前五個元件變體均通過功能檢查，但 graph 內只有矩陣乘法。本輪新增實際 native 的 48 層 mapping／load-recording kernel，搭配 LogicalHistory、CpuGpuEvent、背景事件工作與非同步輸出，再分別只切換 recording、輸出事件 blocking 設定或 graph replay。

四格各完成八 rank × 512 steps，其中 384 steps 在捕捉內；每 rank 觀測 18,432 個 native map／record kernel，八個檢查點逐一核對 mapping 與負載計數。每 rank 四個 worker cycle、192 次退休完成，其中 144 次在捕捉內。未新增 Xid，但仍觀測到 NVRM 警告，不能把這寫成驅動健康證明。

它仍不是完整 B4 worker 或真實 serving。缺少模型 attention／MoE、GPU collectives、真正 planner／weight transfer、allocator／KV 壓力及非阻塞 readiness 排程；合成主迴圈會等待 worker 結果。因此，目前只知道這些元件在所測形狀與排程下尚未重現失敗。

跨 stream 與 CPU 恢復：保留失敗，不補成成功

graph 關閉案例的八 rank 均完成 ordinal 1024–1344，完整 session 已保存。舊 CPU 切片在大量 correlation ID 上反覆掃描，超過原生 300 秒執行 RPC 限制，最後只有 22／24 請求完成。這個失敗狀態沒有被改成通過，也沒有重跑其 GPU 捕捉。

CPU 恢復使用線性 uniqueness 計數和索引式前序活動查找；既有三個真實窗口的切片逐事件一致，另三個窗口的 316 條事件關聯報告也一致。小型 CPU 檢查曾因 JSON tuple／list 表示差異失敗，已保留原檢查並修正比較方式；這不是 GPU 失敗。

恢復出的 1,515 條跨 stream 關聯均有具體 stream 身分與來源活動，使用事件 generation、同執行緒 CPU API 範圍和 native correlation ID。它們不證明可刪除的等待、B4 特有成本或正式比較的剩餘延遲。此失敗案例沒有事後時鐘校準，跨 rank 絕對時間排序仍未知；graph／C++ 內部依賴與背景 CPU annotations 亦不完整。沒有觀測到的邊不填成零成本。

下一個准入條件與研究方向

目前較值得優先追查真實模型 CUDA graph、buffer 生命週期與 profiling 的交互作用，保留實際 MoE／attention 與記憶體配置來繼續縮小；現有證據尚未定位唯一失敗 kernel，也不足以選定 driver、同步或 policy 修復。

四組同配置控制必須等原 graph／原非同步輸出／原 worker 模式的 charged pilot 通過，而且 trace 中確實涵蓋原生提案與 commit，才可繼續。graph 關閉或產生端阻塞的診斷成功都不能替代此准入。目前沒有新 GPU 主測量排隊。
