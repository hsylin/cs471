做了什麼，哪些成功

以事件物件的 generation、record／wait 呼叫及 CPU→CUDA correlation 建立依賴，再以 CUPTI 查詢把具體 stream handle 對應到同一 CUDA context 的 stream ID。缺失、衝突、事件重用或特殊 default-stream 身分保留為未知，不以時間接近代替身分匹配。

成功的 fixed_idle 全模型 pilot 完成 24／24 請求（16 warmup＋8 probe）。八 rank 的三個邏輯窗口一致，長度為 64、64、192 個原生 iteration；排除首尾後為 62、62、190。最低 kernel 關聯率為 98.742%。這是短 LongBench decode 捕捉，不代表持續的早／中／晚期或 mixed 工作負載覆蓋。

跨 stream 證據代表什麼

1,512 條 wait 都能連回來源活動，下一個目的 stream 活動皆為 Memcpy DtoH (Device → Pinned)。來源 GPU 工作在 wait CPU API 返回時仍未完成；其中 1,497 條在先前已觀測到的目的 stream 活動結束後才完成，另 15 條缺少前序目的活動，保留未知。

這確認了輸出拷貝的跨 stream 先後依賴，沒有確認可刪除的等待。它們存在於沒有 B4 管理工作的 fixed_idle 控制；不能把它們算成 B4 特有成本，也不能由此解釋未插樁正式比較的剩餘延遲。

最新失敗排除了什麼說法

最新版本每 rank 只啟動一次 profiler，完全不切換 collection。八 rank 均到達第三個邏輯窗口 ordinal 1152，預定結束 1344；其後未匯出 session，最終由 sample_tokens RPC timeout 結束。kh021 同時期有 NVRM 錯誤，kh023 GPU3 有 Xid 13。沒有事後時鐘校準或可恢復的完整 trace。

因此，反覆啟停 profiler 或 collection toggle 並非出現這類失敗的必要條件。但邏輯窗口的 CPU barrier、邊界 GPU synchronize、事件 hooks、CUDA graph、驅動與應用交互仍未分離；錯誤回報位置與 Xid 本身都不足以定位唯一根因。不同嘗試也不保證同一根因。

charged pilot 的原生 cycle 750 在八 rank 上各有 48 層 commit 完成、hash 一致，但全部發生在第一次捕捉之前。計算提案與實際配置都沒有變動。尚未驗證捕捉期間的 active planner／transfer／commit 共存，也未驗證有變動的 hypothetical candidate 在持續同配置控制中被抑制。
