# Resident-residual input provenance

This selection contains 640 fresh source documents in 20 groups of 32 documents. GSM8K training questions and WildChat each contribute two pilot and eight final groups. The final comparison therefore has 512 documents in 16 main groups. Source selection and arrival assignment were completed before capture or performance measurement, using seeds 471801 and 471802 respectively. No routing statistic or timing outcome entered either selection.

GSM8K is explicitly a **new training-question source frame**, labeled `gsm8k_train`. The fixed model is not trained; only the `question` field is used as a prompt, without the answer. Results from this frame must not be pooled with the preceding test-question studies as if they used the same source population. The remaining test frame had only 103 fresh questions. The remaining MBPP frame had nine tasks and 171 captured token records, insufficient for separate source-disjoint B128 pilot and final banks. MBPP was consequently omitted before new measurements, with no sentinel or MBPP generalization claim.

The WildChat frame remains the first 8,192 rows of that shard, requiring English, a non-toxic conversation and first user turn, and nonempty first-user text. Database terms do not establish separate rights over every conversation's contents. The public manifest records source identities and hashes but omits full selected text and token IDs. Those fields remain in the private capture manifest. Neither this omission nor hashes constitute anonymization.

The exclusion union contains 3,399 previously selected documents: 1,927 unique documents from all three earlier generalization selections, 768 stock-comparison documents, and 704 resident-fix documents. Superseded selections and unused held-out groups remain excluded. All 56 earlier captured source documents are also checked. Excluding the entire original GSM8K test split adds its 103 previously unselected questions, giving 3,558 reference identities. These are document counts, not bank counts.

Full text and model-visible prefixes were checked using NFKC normalization, case folding, whitespace normalization, exact hashes, and five-shingle Jaccard similarity at threshold 0.8. Historical long sources additionally retain first-2,048 and first-512-token views and whole-source exact hashes. One of the 7,473 training questions was rejected as an internal near duplicate; none was exempted from the earlier-source or full-test checks. These checks establish disjointness under the declared comparisons, not semantic independence or absence from checkpoint pretraining.

The tokenizer is pinned to Qwen3-30B-A3B revision `ad44e777bcd18fa416d9da3bd8f70d33ebb85d39`, with tokenizer JSON SHA256 `aeb13307a71acd8fe81861d94ad54ab689df773318809eed3cbe794b4492dae4`. Selection uses tokenizers 0.23.3, no chat template, and no added special tokens. Documents require at least eight tokens and retain at most the first 512. The selected groups contain 1,676–1,981 GSM8K-training records and 2,162–5,453 WildChat records. Each prefix is processed causally as a separate prompt, with no cross-document attention.

The capture mechanism executes the pinned BF16 embedding, layer-0 attention, normalization, and router and records the expert-input hidden vectors with source positions and numerical/hash attestations. The timed runtime consumes captured hidden vectors only and computes its actual vLLM gate, top-k, and combining weights. Captured HuggingFace routes are provenance, not injected runtime choices. Capture validity and runtime validity remain separate obligations. No new capture had run when this source-selection audit was completed.

The planned 16 warmup plus 4,096 measured B128 layer jobs are constructed from these bounded banks with seed 471803. Records may repeat across jobs; they must not repeat within a job. Exact job-index and per-record reuse artifacts are required at preparation. This construction is not a collection of 4,096 natural requests, and fresh source documents do not make repeated token occurrences independent observations.

Arrival selection uses the original [Azure code CSV](https://github.com/Azure/AzurePublicDataset/releases/download/dataset-llm-2024/AzureLLMInferenceTrace_code_1week.csv) and [conversation CSV](https://github.com/Azure/AzurePublicDataset/releases/download/dataset-llm-2024/AzureLLMInferenceTrace_conv_1week.csv), under the [recorded CC-BY and attribution instructions](https://github.com/Azure/AzurePublicDataset/blob/215becdacba1ce682c7368642ce97d5a332de7a6/AzureLLMInferenceDataset2024.md), including DynamoLLM, HPCA 2025. Both complete files were scanned: 16,803,695 code rows and 27,303,999 conversation rows. Candidate intervals contain 4,096 contiguous release rows and one following boundary row and do not cross UTC dates. All 184 earlier intervals, including their boundary rows, are excluded. Of 4,096 code candidate bins, 98 overlap earlier intervals; of 6,660 conversation bins, 93 overlap. A hash-selected nonpositive horizon or terminal gap fails instead of triggering replacement.

Each content group receives one code and one conversation interval, shared across arms and declared loads. The 40 assigned intervals contain 163,840 release rows and 40 boundary rows: eight pilot and 32 final intervals. Original timestamps, ties, offsets, request-length metadata, and row hashes are preserved. The first two source dates per service supply pilot intervals and the last five supply final intervals. Each dataset/service final subset covers all five final dates. These are new rows within previously used public weeks, not new production dates or organizations. Code dates are May 10–16, 2024; conversation dates are May 12–18. The service-specific splits overlap in actual date, so any date sensitivity must treat the same actual date jointly across services.

Azure contains no matching customer text. One release is paired with one constructed fixed-token layer job; original context/generated lengths remain metadata rather than executed lengths. This pairing does not recover the original content–arrival dependence. Claims remain conditional on the pinned layer/checkpoint, two-H100 setup, constructed inputs and declared calendar scaling.

The independent same-team CPU audit reconstructed all 640 selected texts from pinned raw records, retokenized them, repeated full/prefix duplicate checks, rehashed both entire arrival CSVs, and reconstructed all 163,880 selected rows and boundaries. It passed, as did six focused source-split/failure tests. All 83 preceding frozen execution files remained byte-identical. This verifies source artifacts, not GPU execution or performance, and is not external-laboratory replication.

These hashes identify selected inputs, not a completed performance experiment.

## Completed capture attestation

All 20 banks were subsequently captured in allocation 4872248, step 38, on kh014: four pilot banks contain 13,154 authenticated token records and 16 final banks contain 44,320, totaling 57,474 records from all 640 documents. The [independent capture audit](capture-audit-v1.json) passed remotely on CPU for every bank. It checked file and content digests, exact source tokens and positions, finite BF16 hidden bits, combining-weight encoding, recorded native-boundary/router/manual-router/serialization attestations, and checkpoint/implementation pins. The gate tensor matches the earlier independently hashed safetensors byte range. This audit does not independently recompute attention or recapture hidden states on GPU.

The [capture ledger](capture-run-ledger-v1.json) records both split indexes, provenance hashes, hardware-log identities and audit scope. Capture ran from a source-only working-tree snapshot with no commit label; exact file hashes and archived capture-script bytes identify that snapshot. The public indexes, provenance, logs and audit are stored here. Bank payloads remain on the server and were not downloaded during this audit; offline replay requires those authenticated files. No final routing-demand summary or performance outcome was used in capture validation.
